## Context

Flutter scaffolds both platforms by default, so `brainy-app/android/` exists whether or not anyone intends to ship it. What turns scaffolding into an implied commitment is the surrounding documentation.

Evidence that Android is intended: `ci-cd.md` says Android CI is "not yet" configured; `leaderboards.md` describes Google Play Games alongside Game Center; the `games_services` package supports both; `deploy-testflight.yml` watches `brainy-app/android/**`.

Evidence that it is not: `android/app/` holds only `build.gradle.kts` and `src`; there is no keystore configuration, no Play Console pipeline, no Android workflow, no release history. The App Store metadata, fastlane setup, monitoring workflow and the entire release process are iOS-only. The stated direction is completing the iOS product.

The path filter is the one place this ambiguity does something concrete and wrong: a change touching only Android files triggers a macOS runner to build and upload an iOS build to TestFlight.

## Goals / Non-Goals

**Goals:**
- Record an explicit decision.
- Remove the ongoing tax of an undeclared maybe.
- Fix the path filter either way.

**Non-Goals:**
- Making the decision. It is a product and business call — market, audience, capacity — not a technical one. This change forces it to be made and recorded.
- Building an Android pipeline. If the answer is yes, that is a separate, substantial change.
- Removing `brainy-app/android/`. Flutter regenerates it, and deleting scaffolding to signal intent is a poor mechanism; a stated decision is the right mechanism.

## Decisions

**Force the decision rather than default to one.** The current state is not neutral — it costs a little on every change and delivers nothing. Either answer is better than continuing to hedge.

**If the answer is no, keep the `android/` directory but state its status.** Deleting it fights the framework and would be regenerated by the next `flutter create` style operation. Documenting it as unbuilt scaffolding costs one sentence and removes the ambiguity entirely.

**Fix the path filter under either outcome.** If Android is unsupported, `brainy-app/android/**` should not trigger an iOS deployment. If Android is supported, it should trigger an *Android* build, not an iOS one. The current configuration is wrong in both worlds.

**Do not preserve Play Games documentation "just in case".** `leaderboards.md` describing an unconfigured integration is the same defect as the rest of `plans-code-sync`: documentation asserting something untrue. If Android arrives later, the documentation arrives with it.

**Consider the iOS-only consequence for `games_services`.** The package supports both platforms; that is fine and needs no change. But if Android is dropped, the leaderboard documentation should describe Game Center specifically rather than an abstraction over two services the app only ever uses one of.

**Sequence alongside `plans-code-sync`.** Both correct plan text. This one supplies the decision that determines what `leaderboards.md` and `ci-cd.md` should say about Android; keeping it separate means the decision is recorded as a decision rather than buried in a documentation sweep.

## Risks / Trade-offs

- **Declaring Android unsupported closes a door** → It does not: the code is cross-platform Flutter and the decision is reversible at any time. What is removed is only the implication that work is owed.
- **Declaring Android supported creates real obligations** → Signing, Play Console, a build workflow, Play Games leaderboard configuration and device testing. That is the honest cost, and naming it is the point of forcing the decision.
- **Someone later assumes Android works because the directory exists** → Mitigated by stating the scaffolding's status explicitly.
- **Changing the path filter breaks a build trigger someone relies on** → No one can be relying on Android paths triggering an iOS build; that behaviour is a bug.

## Migration Plan

1. Owner decides: supported, or not.
2. If not: remove the Android line from `ci-cd.md`; remove Play Games from `leaderboards.md`; state the scaffolding's status; drop `brainy-app/android/**` from the deploy path filter.
3. If yes: create a separate change scoping signing, Play Console, the build workflow, Play Games configuration and device testing; correct the path filter to trigger an Android build.
4. Record the decision in `CLAUDE.md` so it does not need making again.

**Rollback:** documentation and one workflow filter line; trivially revertible.
